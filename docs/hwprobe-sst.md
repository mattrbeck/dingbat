# hwprobe-sst: the SingleStepTests ARM7TDMI disagreements, asked of an AGB SP

The SingleStepTests ARM7TDMI vectors (tests/README.md, "SingleStepTests") were
generated by running a reference emulator, not captured from hardware. Where
dingbat and the vectors disagree, this probe asks the console. Each cell is a
few instructions run from IWRAM on the AGB SP over the GB-Link rig
(`tools/hwlink`), with every answer read back as one 32-bit word, so the
whole table is one self-contained probe that anyone can rerun:

| File | What it is |
|---|---|
| `tests/roms/payloads/sst.s` | groups A and B: 96 cells that always come back, by themselves or through the watchdog |
| `tests/roms/payloads/sstrisk.s` | group C: 7 cells where an undefined-instruction trap or a jump into the BIOS is a possible answer; uploaded on its own and run last |
| `tests/roms/payloads/sst.inc` | the frame both share: saves and restores every bank, SPSR, IME, IE, the timers and the IRQ vector; the watchdog |
| `tools/hwlink/sst.py` | runs the cells in dingbat (`emulators`), on the console (`console`), prints them side by side (`show`), builds cartridge ROMs of both payloads (`rom`) |
| `tools/hwlink/sst-dingbat.json` | dingbat's answers (HLE BIOS and the real BIOS) |
| `tools/hwlink/sst-agb.json` | the console's, recorded 2026-10-12: every answer with its count over three runs |

`python3 tools/hwlink/sst.py rom DIR` builds `sst.gba` and `sstrisk.gba`,
cartridge ROMs that run every cell of a payload once, in order, and store
the answers as words from 0x02000000 (then 0x600D0000 at 0x02000FFC). They
draw nothing; they are for running the same code in an emulator.

## Running it on the console

Before a console run, after any change to the payloads or to `sst.py`:
`python3 tools/hwlink/sst.py monitor-sim` plays the run's exact link
traffic into the monitor's own code (`tests/roms/gbamon.s` with only its
serial routine replaced by a scripted host, `tools/hwlink/monsim.py`) in
dingbat with the HLE and the real BIOS, and checks every cell answers as
the cartridge wrapper does. `--mode=` picks the CPU mode it starts the
monitor in (System by default; the multiboot entry's mode is not pinned).

1. Power the SP on with **no cartridge** in the slot. Connect the GB-Link.
2. `cd tools/hwlink && python3 monitor.py install` (the screen turns green),
   then `python3 monitor.py ping` should print `PONG`.
3. `python3 sst.py console`. It first runs a smoke test (a two-instruction
   payload called twice through one upload) and stops if that fails. Then
   group A (three passes), group B (three passes), then group C one cell at
   a time, three runs each, least risky first, writing `sst-agb.json` after
   every answer. It reads the trampoline back before every call and the
   whole image back after a group's first call and after every pass, and
   stops, with the console still answering, if the payload has changed
   itself. It takes a few minutes.

The first console run (2026-10-12) stopped at the second cell,
`t.str_r0.iw`, with the console wedged. The cause was the harness: the
variables block at the end of the image was 128 bytes, `save_banks` wrote
144, and the overflow overwrote the first four words of the trampoline
the runner puts after the image and calls through without uploading
again. `monitor-sim` reproduces that run (cell 1 never comes back) and
passes every cell since the variables moved to scratch IWRAM; the guards
above stop that kind of run before its second call.
4. `python3 sst.py show` prints every cell with dingbat's answer beside the
   console's (`<<<` where they differ).

If a cell never comes back, the run stops there and names the cell. The
console then needs a power cycle and `monitor.py install`; every answer up
to that cell is already in the file. To carry on with the cells after it:
`python3 sst.py console --groups=C --keep --skip=<the cell>`.

### Risk notes

- Groups A and B cannot leave the console stuck unless the CPU masks
  interrupts on its own: every cell either returns or runs with CPSR.I
  clear under the **watchdog**, TM3 raising an interrupt 16384 cycles
  later, whose handler (called by the BIOS's IRQ dispatcher) takes the CPU
  back to System mode and the cell's continuation. User-mode cells leave
  that way by design. Self-modifying cells (the r15-base stores, SWP with a
  base of r15) put their code back, and the runner re-reads the payload
  after every pass and uploads it again if it changed.
- The BIOS's undefined-instruction vector, with no debugging cartridge in
  the slot, returns with `SUBS PC, LR, #4` (GBATEK, "GBA Cartridge Header"
  09Ch: the handler forwards to a cartridge only when the header's debug
  bits are set). From ARM that is the undefined instruction again, an
  endless loop; from Thumb it is the halfword before the instruction. So:
  - **CP14 (x.mrc14\_\*, x.mcr14\_c1)**: GBATEK says CP14 does not trap. If
    it does, the loop runs with I clear and the watchdog ends it, reading
    the trap off R14_und. Lowest risk of group C, run first.
  - **Thumb `DExx` (x.thumb_dexx)**: the halfword before it is `bx r5`, so
    a trap returns there and escapes; a branch lands on `bx r3`, a fall
    through on `bx r2`. Every outcome returns a value.
  - **MRS into r15 (x.mrs_r15)**, run last: `mrs pc, spsr` in SVC mode with
    SPSR_svc = 0x00000010. A write of that value to r15 sends execution to
    0x10, the BIOS vector that branches into the same handler, which
    returns (to R14_svc - 4, set to land on a pad) in User mode with I
    clear, where the watchdog takes over. The value is word-aligned, so
    how r15's low bits are taken does not come into it. The residual risk
    is an answer nobody predicted that masks interrupts.
- The worst case for any cell is a wedged console: a power cycle and a
  reinstall, no damage.

## The cells and the four answers

Columns: **dingbat** is this branch with the real BIOS (`sst.py
emulators`; the HLE BIOS answers the same), after the two fixes the
console asked for (u.rs15_lsr, x.mrs_r15 on the HLE BIOS; below). **Vectors**
is what the SingleStepTests ARM7TDMI vectors (rev `e3097d8`) do for the same
instruction, read from the vector files (`~/.cache/dingbat-singlestep`) or
the known-divergence bucket in `tests/singlestep_arm7.nim`, and applied to
the cell. **GBATEK** is what GBATEK states, or "-" where it states nothing
for ARMv4. **AGB SP** is the console (`sst-agb.json`, 2026-10-12): three runs a cell, every cell answered the same each time.
A = the address of the instruction tested.

### 1. r15 stores: timing and the value stored

read by an `ldrh` around four copies of the instruction, all from IWRAM.
`t.ctrl` / `t.thumb_ctrl` time nothing (the Thumb ones include the two
`bx`). Per instruction = (cell - control) / 4. Destination `iw` is IWRAM
(0x03006400), `ew` EWRAM (0x02030400, 2 wait states: 3/3/6 cycles for

## Where dingbat and GBATEK disagree

- **Thumb `cmp pc, r0`** (r.thumb_cmp_pc.\*): GBATEK describes a compare;
  dingbat restores the CPSR from the SPSR, as the AGB SP did (THUMBPC,
  THUMBPC2, THUMBPC3).
- **MRS into r15**: GBATEK says every write to r15 is forcibly aligned;
  dingbat's MRS path writes r15 unaligned (an UNPREDICTABLE encoding, and
  only seen with a CPSR source; x.mrs_r15 avoids it).
- Everywhere else GBATEK is silent (the encodings it calls not allowed:
  TSTP-style with Rd = r15, r15 as Rs, a multiply or SWP operand or an MRS
  destination, r15-base writeback, User/System S-bit returns, reserved PSR
  bits) or agrees with dingbat (store timing and values, CP14, the six
  smaller fixes, Thumb `DExx` being undefined).
